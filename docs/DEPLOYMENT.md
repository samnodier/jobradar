# Personal deployment and recovery

## Configure first

Use an always-on Linux host, or accept that a sleeping laptop cannot fetch or send until it wakes and the application restarts. Keep one application replica for this personal release.

Copy `.env.example` to `.env`. Set a strong database password (URL-encode reserved characters if constructing DB_URL yourself), a generated stable encryption key, GitHub OAuth credentials, the public HTTPS `APP_BASE_URL`, the matching `ALLOWED_ORIGINS`, and `GITHUB_REDIRECT_URL=https://your-domain/auth/github/callback`. Set `PERSONAL_EMAIL` to the email returned by your GitHub login. Set `DIGEST_RECIPIENT` to that registered account's email and configure the chosen sender. Start with delivery disabled.

The production Compose DB_URL interpolates the password into a URI, so use a strong hexadecimal password (for example generated by `openssl rand -hex 32`) there to avoid URI interpolation problems. Never commit `.env` or put provider keys in frontend variables.

## Start the production stack

```sh
docker compose -p jobradar -f compose.production.yml up -d db redis
docker compose -p jobradar -f compose.production.yml --profile tools run --rm migrate up
docker compose -p jobradar -f compose.production.yml up -d --build app
```

The migration container is built from `Dockerfile.migrations`. On first use Docker may need time to download Go dependencies. The app image includes static Vue assets, CA certificates and timezone data and runs as an unprivileged user. It does not require Node, Goose or a local model at runtime.

Put an HTTPS reverse proxy in front of `127.0.0.1:8080`. For a Caddy service installed on the same host, a site block is:

```caddyfile
your-domain.example {
    reverse_proxy 127.0.0.1:8080
}
```

Use your actual domain, configure DNS and the OAuth callback, and ensure the proxy can obtain its certificate. In production, Secure cookies require HTTPS. PostgreSQL and Redis are not published to the host by production Compose.

## Verify before enabling email

1. Visit `/api/health`, sign in, complete your profile, and check System Status.
2. Verify jobs appear and scores are populated. Wait until the matching backlog drains.
3. Add Adzuna credentials/searches and a small optional Greenhouse watchlist, recreate the app, then check source health.
4. Preview the digest on the dashboard. A preview sends nothing. Confirm the destination in `.env` and the sending account's verified sender setup.
5. Set `DIGEST_ENABLED=true` and recreate the app. The background scheduler will deliver after a configured profile-local hour. For an immediate cycle:

```sh
docker compose -p jobradar -f compose.production.yml run --rm app --digest-once
```

One digest per configured local-date/hour slot is enforced even if you run the command twice. Profile → Settings controls one or two daily hours, timezone and the score threshold. Jobs are reserved across all slots so morning results do not repeat in the evening. Empty or low-score results do not produce mail. This is intentional; do not clear delivery records just to force duplicate messages. Check the dashboard's persisted state and the provider's message history. Check spam as well as inbox.

Live OAuth, Adzuna access, and inbox delivery require your accounts and cannot be established solely by tests using fake providers.

## Choose an email provider

Resend has a small transactional API and documented idempotency support. Its free daily allowance is more than sufficient for one personal daily digest; verify the current plan at [Resend pricing](https://resend.com/pricing). A verified sender/domain may be required depending on the account and destination.

GoHighLevel is reasonable if your sub-account already sends email successfully. Create a private integration token with `contacts.readonly` and `conversations/message.write`, and configure your own contact ID and sender. The adapter checks the contact's email against DIGEST_RECIPIENT before sending. Confirm costs inside your existing account: API access is not a promise that the account's email delivery is free. See [send message](https://marketplace.gohighlevel.com/docs/ghl/conversations/send-a-new-message/) and [get contact](https://marketplace.gohighlevel.com/docs/ghl/contacts/get-contact/).

Self-hosting SMTP is possible, but is unnecessary for this release. It introduces DNS authentication, IP reputation and deliverability maintenance.

## Failure recovery

- **Redis outage or killed worker:** PostgreSQL retains pending matching. The dispatcher retries delivery; previously enqueued tasks become eligible after five minutes. Duplicate tasks are serialized and acknowledge only the processed revision.
- **Bad AI key/outage:** job collection, matching and email continue. Automatic AI enrichment is off by default. Provider errors do not change deterministic match scores.
- **Email `pending`:** a retry is scheduled. The exact persisted payload and key are reused.
- **Email `sending`:** the provider request may be in flight; after interruption, recovery waits for the delivery lease. Resend can be retried within the safe window; GoHighLevel becomes uncertain.
- **Email `uncertain`:** inspect the provider's send history. If it accepted the message, mark that digest sent with the provider message ID. If absence is confirmed, choose a deliberate recovery action; do not blindly reset all digests.
- **Email `failed`:** inspect the sanitized error and correct credentials/sender/configuration. A reviewed reset of that one digest may be appropriate while its idempotency window is valid. Old attempts outside the window require explicit reconciliation; never bypass the safety check casually.
- **Changed provider/sender:** pending deliveries are held for review rather than sent through a different account automatically.
- **No digest:** check recipient matches the signed-in account, master notifications and profile email delivery are enabled, source health, pending matches, score threshold, posting age and whether those jobs were already reserved for an earlier digest.

The ledger favors avoiding duplicates when delivery is uncertain. It cannot guarantee exactly-once delivery across a database and an arbitrary email provider. Backing up/restoring old ledger state may also require reconciliation with provider history.

## Back up and restore

Before migrations, take a database backup and separately secure the encryption key and environment configuration. Example (replace `sam` and `jobradar` if configured differently):

```sh
docker compose -p jobradar -f compose.production.yml exec -T db pg_dump -U sam -d jobradar -Fc > jobradar-backup.dump
```

Restore into a NEW empty database/isolated stack first, using `pg_restore -U sam -d jobradar` with the dump on stdin. Verify login/profile/job counts and delivery ledger state before switching the app to that restored database. Do not run destructive reset commands against the only copy of your data. `docker compose down` preserves named volumes; `down -v` deletes them.

The development `./pgdata` directory and production named volume are separate. To bring development data into production, use a logical pg_dump/pg_restore migration; do not copy a live PostgreSQL data directory between containers.

## Continuous deployment

Pushing to `main` deploys without logging in to the server:

1. GitHub Actions (`.github/workflows/ci.yml`) runs the backend integration tests, vet, frontend tests and the production build on every push and pull request.
2. Only for `main`, and only after every test passes, it publishes `ghcr.io/<owner>/jobradar` and `ghcr.io/<owner>/jobradar-migrate`, tagged `main` and the commit SHA.
3. On the server, a user systemd timer runs `deploy/update.sh` every five minutes. It fast-forwards the checkout to `origin/main` (Compose file and scripts), pulls the images, and when something changed: backs up the database, runs migrations, recreates the app and waits for `/api/health`. Otherwise it does nothing.

The server needs no inbound port and no GitHub credentials while the repository and its packages are public. A self-hosted Actions runner is deliberately not used: on a public repository, pull requests could run code on the host.

One-time server setup:

```sh
git clone https://github.com/<owner>/jobradar.git && cd jobradar   # stays on main
cp /path/to/production.env .env && chmod 600 .env
sudo loginctl enable-linger "$USER"   # timers run without a login session
./deploy/update.sh                    # first deploy (pulls images, migrates, starts)
./deploy/install-systemd.sh           # update timer (5 min) + nightly backup timer
```

Watch it: `journalctl --user -u jobradar-update -f` and `systemctl --user list-timers`. Deploy a fix by merging to `main`; it is live within about ten minutes (CI plus the next timer tick). Pin a version with `JOBRADAR_TAG=<commit sha>` in `.env`.

If the first pull is denied, the container package is private: make it public in the package settings on GitHub, or `docker login ghcr.io` on the server with a read-only `read:packages` token.

Rollback: set `JOBRADAR_TAG` to the previous good commit SHA and run `./deploy/update.sh`. An image rollback does not undo a schema migration; restore the pre-deploy backup if a migration must be reversed.

Nightly backups go to `~/jobradar-backups` (14 kept; override with `BACKUP_DIR`/`BACKUP_KEEP`). They are on the same disk, so copy them off the host regularly.

## Public access without opening ports

The app listens on `127.0.0.1:8080`; set `JOBRADAR_PORT` in `.env` if another service already uses that port. Two ways to publish it over HTTPS without router port forwarding:

- **Tailscale Funnel:** `sudo tailscale funnel --bg 8080` gives `https://<machine>.<tailnet>.ts.net`. Use `tailscale serve` instead to keep it private to your own devices.
- **Cloudflare Tunnel:** `cloudflared` maps a hostname in a Cloudflare-managed domain to `http://127.0.0.1:8080`.

Then set `APP_BASE_URL`, `ALLOWED_ORIGINS` and `GITHUB_REDIRECT_URL` to the public HTTPS address, and keep `APP_ENV=production` so cookies are `Secure`. A GitHub OAuth app has a single callback URL, so use a separate OAuth app for production (or rely on email/password login there).

Only one machine may run the digest scheduler: production sets `DIGEST_ENABLED=true`; every development machine sets it to `false`.
